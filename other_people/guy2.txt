Flat RAG pipelines index and retrieve data faster than others but struggle with cross-reference questions in structured documents. However, one improvement significantly enhances cross-reference resolution by using an LLM at index time, amortizing the cost over the corpus rather than per query. Surprisingly, this simple idea was independently published this week as IndexRAG (https://arxiv.org/abs/2603.16415)

Let's consider an example I met in practice. Articles A and B in a legal corpus with 300 documents are connected  by a table that maps penalties  between them. The indexer puts chunks of A, B, and the table into the vector store. When a question targets A but the answer requires B, retrieval returns A and the table but not B. The query has no vector match with B because nothing in the query text points to it directly. Only the table mentions the link.

The obvious fix is agentic iteration. Retrieve the table, notice it references B, fire a second retrieval for B, merge results. This works, but it multiplies LLM calls per query.

The better move is to pay that cost once, at index time. During indexing, scan each unvisited table row and generate a fact chunk that merges the row with the referenced chunks from the linked articles. This may seem to produce many duplicates, but semantically similar chunks are trivial to detect and skip at index time. The result is an index where a single query can return both sides of a cross-reference, without extra LLM calls at runtime.

A vector index over 300 documents fits in a few hundred megabytes. Even if nearly every third chunk contains a table reference that expands to 10x the original tokens, this approach still remains affordable in terms of memory storing.
